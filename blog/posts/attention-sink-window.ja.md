長い系列で Attention を全部持たない、という選択があります。スライディング窓、StreamingLLM の **attention sink**、そして「先頭数トークンだけは残す」。RoPE で位置を伸ばす話とは別に、**どの過去を、物理的に捨てるか** の話です。捨て方を間違えると、システムプロンプトが途中で消えます。

## 窓だけ切ると、何が壊れるか

窓幅 \(w\) のスライディング注意は、位置 \(t\) が \(t-w\) より前を見ません。計算と KV は \(O(T w)\) です。会話が \(w\) を超えると、冒頭の役割指示・禁止事項・ツール定義が、窓の外に出ます。モデルは直近のユーザー文だけを見て、丁寧に方針を破ります。

「要約して窓に戻す」は一つの対処です。要約モデルが方針を落とすと、本体は忠実に、誤った要約に従います。評価は、窓を超えたあとの拒否セットで取ります。窓の内側だけ測っても、この失敗は見えません。

## Sink が残すもの

観察として、softmax は **最初の数トークン** に、内容と無関係な質量を置きがちです。StreamingLLM（Xiao ら）は、これを sink と呼び、窓を滑らせても先頭数トークンの KV は残します。直近 \(w\) と、先頭 \(s\) だけが生きている、というキャッシュです。

$$
\mathrm{visible}(t) = \{1,\ldots,s\} \cup \{t-w+1,\ldots,t\}
$$

RoPE の位置 ID を、捨てた分だけ詰め直すか、絶対位置のままにするかは実装依存です。詰め直すと、相対位置の意味が「実際の距離」からずれます。[RoPE](post.html?slug=rope) の伸ばし方と、同時にいじると、原因が二つになります。どちらか一方から試します。

Sink は魔法ではありません。先頭が BOS とシステムプロンプトの頭だけだと、途中の「部署Bの文書は使うな」は、まだ窓の外です。システムプロンプトは短く、重要な制約は **先頭側に寄せる** か、毎ターン再注入します。再注入は KV を増やすので、同時接続の見積もりに入れます。

## プレフィックスキャッシュとの関係

同じシステムプロンプトを、全リクエストで使い回すなら、その KV を prefix cache に置きます。窓と共存させるときは、「捨ててはいけない区間」を cache の境界と一致させます。境界がずれると、あるリクエストだけ方針が残る、という再現不能になります。

## 見る場所

- 窓幅、sink 数、位置 ID の再番号付けの有無
- システムプロンプトの長さが、sink + 再注入のどちらで守られているか
- 学習がフル注意なのに、推論だけ窓、になっていないか（分布が違う）
- 8k を超えた拒否と、引用の評価を、窓の内側と外側で分ける

長文対応と、窓は別物です。前者は位置の外挿、後者は過去の破棄です。カタログの「128k」がどちらを指すか、重みとエンジンで確認します。
