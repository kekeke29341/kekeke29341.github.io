ローカルLLMの見積もりで、よく最初に見るのは重みのギガバイト数です。70B を FP16 で載せるなら約 140GB、AWQ 4bit ならその四分の一、という話です。同時接続と長いコンテキストを載せた瞬間に先に足りなくなるのは、多くの場合 **KV cache** です。

この記事では、KV がなぜ系列長とバッチに比例するのか、MHA / MQA / GQA で何が減るのか、をメモリの式から書きます。

## Attention は、過去の K と V を覚えている

デコーダの自己注意は、新しいトークン \(t\) に対して、それまでのすべての位置の Key / Value を使います。生成を \(T\) トークン続けるとき、毎回先頭から計算し直すと \(O(T^2)\) の計算がそのまま乗ります。そこで過去の \(K, V\) を GPU メモリに残します。これが KV cache です。

1トークン増えるたびに足す量は、おおまかに次です。

$$
2 \times L \times H_{\mathrm{kv}} \times d_{\mathrm{head}} \times b \times \mathrm{bytes}
$$

- \(2\): Key と Value
- \(L\): 層数
- \(H_{\mathrm{kv}}\): KV のヘッド数
- \(d_{\mathrm{head}}\): ヘッド次元
- \(b\): 同時に抱えている系列数（バッチ、あるいは同時セッション）
- bytes: FP16 なら 2、FP8 なら 1

重みはリクエストが来ても増えません。KV は **同時接続 × コンテキスト長** で増えます。100人がそれぞれ 8k トークン近くまで話すと、重みより KV の方が大きい、は十分あり得ます。

## MHA、MQA、GQA

元の Multi-Head Attention（MHA）は、Query のヘッド数 \(H_q\) と KV のヘッド数が同じです。ヘッドを増やすほど表現は増えますが、cache も線形に増えます。

**Multi-Query Attention（MQA）** は KV を全 Query ヘッドで共有します。\(H_{\mathrm{kv}} = 1\)。cache は劇的に減ります。代わりに、ヘッドごとの「何を見るか」の多様性が落ちます。

**Grouped-Query Attention（GQA）** はその中間です。Query ヘッドを \(g\) グループに分け、グループごとに KV を1本持ちます。Llama 3 系がこれを使っています。メモリは MHA の \(H_{\mathrm{kv}} / H_q\) 倍です。

| 方式 | \(H_{\mathrm{kv}}\) | cache | 表現 |
| --- | --- | --- | --- |
| MHA | \(H_q\) | 最大 | ヘッドごとに独立 |
| GQA | \(H_q / g\) | 中間 | グループ内で共有 |
| MQA | 1 | 最小 | KV は1本 |

「同じ 70B」でも、GQA かどうかで 8k・同時100 の可否が変わります。モデルカードの `num_key_value_heads` を、パラメータ数より先に見ます。

## 計算より、メモリ帯域が先に死ぬことが多い

生成の1トークンは、巨大な行列を一度ずつなめるだけです。算術強度が低く、ボトルネックは GPU の演算器より **HBM から KV を読む帯域** になりやすい。だからこそ、

- PagedAttention（vLLM）で断片化を減らし、実効バッチを稼ぐ
- prefix cache で、同じシステムプロンプトの KV を使い回す
- KV を FP8 や量子化で縮める

が、量子化以上に効く現場があります。逆に、KV を粗くすると長文の途中から位置情報が先に死ぬことがあります。[RoPE](post.html?slug=rope) の回転は Q/K の積なので、K の精度は位置そのものです。

## 見積もりの順番

1. 同時に何系列か、各系列の最大長は何か
2. \(H_{\mathrm{kv}}\) と層数から、KV のバイト数を出す
3. 重み＋KV＋活性化が、1枚の GPU に載るか
4. 載らないなら、量子化より先に「同時数を減らす / 長さを切る / GQA のモデルに替える」を比較する

スループットの話をするときは、tokens/s だけでなく、**何人を何トークンまで同時に抱えたときの tokens/s** を書きます。片方だけの数字は、KV を無視しています。
